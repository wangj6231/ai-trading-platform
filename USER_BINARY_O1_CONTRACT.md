# F5-B O1 — authorized binary store/read/inspect

TEST_SEAMS_CONFIRMED. O1-A admission/replay remains accepted PASS. Only USER_UPLOAD is implemented here; O2/O3, automatic snapshots, signed URLs, object deletion, orphan cleanup, cloud selection and new persistence schema are excluded.

Public server-module interface: `UserBinaryService.store(principal, account_id, trade_id, upload_id, stream)`, `read(principal, account_id, trade_id, attachment_id)` and `inspect(...)`. Principal is authenticated server dependency output, not browser identity. Upload ID is bounded retry context only; account/trade ownership is rechecked from current server records before IO and final admission/access. No caller key/path/hash/MIME/READY receipt is accepted.

Binary IO is an injected private external interface: create-only `put_if_absent` and scoped `open`, both with finite timeout input. No production provider is selected. Local test IO/failure fixtures are not deployed storage evidence. External IO must honor deadlines; cooperative deadline checks cannot preempt an arbitrary blocking adapter/stream or native decoder. Do not add unbounded timeout threads.

Server derives opaque attachment identity from scoped upload retry context and a scoped binary key containing a server-computed SHA-256 reference. The immutable existing Journal key/size/MIME receipt binds expected bytes without adding O2 version/origin schema. These keys are internal opaque references, never paths or public URLs. Legacy keys without this typed key convention remain NOT_READY/unverified, not retroactively certified. O1 does not attest provider object versions or automatic snapshot origin.

Named infrastructure limits, predeclared before RED: MAX_ATTACHMENT_BYTES = existing 10 MiB; STREAM_CHUNK_BYTES = 64 KiB; MAX_STREAM_READS = 1,024 (bounds tiny-read amplification); SPOOL_MEMORY_BYTES = 1 MiB; MAX_IMAGE_PIXELS = 16,777,216; MAX_IMAGE_DIMENSION = 8,192; MAX_DECODED_IMAGE_BYTES = 64 MiB; IO_TIMEOUT_SECONDS = 10; OPERATION_TIMEOUT_SECONDS = 30. Only static PNG/JPEG/WebP, supported <=4-byte-per-pixel decode modes. Reject animation/multiframe, malformed/truncated images and over-budget inputs; no new MIME class. Temporary request buffers close on all outcomes; this never deletes a committed/staged external object. These are schema/resource safety limits, not StrategyConfig parameters.

Success occurs only after bounded input validation, sniffed MIME, stored readback size/hash verification and committed authorized final receipt. Closure before final admission rejects new receipt and leaves any written object as orphan inventory only. Exact committed replay returns original receipt even when binary later becomes unavailable; it does not repair or overwrite objects.

Historical metadata status and current binary availability are separate. `AVAILABLE` requires a complete verified current read; `UNAVAILABLE` covers missing/corrupt/unreachable binary; `NOT_READY` covers absent/unverified/non-USER_UPLOAD receipt. No failure rewrites historical READY. Read delivers no corrupt prefix or fabricated empty bytes. Inspection performs current IO; it is not historical availability proof or snapshot evidence. Read/store errors are bounded/redacted codes without paths, tokens, keys or exception payloads.

One public behavior RED → minimal GREEN → VERIFY → GRILL at a time. Literal image bytes and precomputed independent size/hash are oracles; established Paper/lifecycle/Journal output protects financial invariants. Actual-PG tests use this same public O1 interface, not new O3 adapter/raw-SQL certification. Complete evidence is recorded in PRODUCT_FOUNDATION_F5_B_REPORT.md.

## Decoder and availability details

PNG/JPEG/WebP are sniffed using the decoder format allowlist, never upload labels. Header dimension/pixel budgets and static-frame checks precede decoding; verification is followed by reopening and full pixel loading, since verification alone does not prove complete pixel data. This follows the [Pillow Image contract](https://pillow.readthedocs.io/en/stable/reference/Image.html). The decoded budget is a conservative four-byte-per-pixel image budget, not a claimed hard process-RSS bound or native-code sandbox. No EXIF stripping or content rewriting is introduced; hashes describe original admitted bytes.

Read validates complete size/hash into a bounded temporary spool before returning bytes (maximum 10 MiB). `inspect` uses the same verified-read path and may temporarily allocate that bounded response; it is not a constant-memory metadata-only lookup. No durable process cache is added. A successful read means bytes verified during this request, not a promise about future object durability.

The 30-second monotonic operation budget is cooperative: checked around stream reads, after decoding, before admission and on read completion. IO receives a timeout capped at ten seconds or remaining budget. External IO must enforce that timeout throughout its stream lifetime. These checks cannot interrupt a nonconforming blocked input/provider/native decoder; deployment adapter certification and request/concurrency admission remain separate. Database operations retain their existing transaction/time/resource boundaries. A receipt that committed successfully is durable even if a later response/access check fails; exact authorized retry recovers it.

Fixed failure codes include INVALID_ATTACHMENT_IDENTIFIER, INVALID_BINARY_STREAM, INVALID_IMAGE, ATTACHMENT_TOO_LARGE, BINARY_STREAM_BUDGET_EXCEEDED, BINARY_OPERATION_TIMEOUT, BINARY_STORE_UNAVAILABLE and BINARY_STORE_VERIFICATION_FAILED. Scope failures use ATTACHMENT_FORBIDDEN; financial closure remains ACCOUNT_CLOSED. External exception messages are suppressed. Missing/corrupt/store-unreachable reads return their distinct typed UNAVAILABLE reasons; no readable prefix is returned. Current ownership is rechecked before both verified delivery and failure diagnostics. Historical READY metadata is never changed by these checks.

An external write/readback precedes the locked DB admission; it is not a distributed object/DB transaction. Closure, revocation, conflict or DB failure can leave external orphan objects, which are not trusted receipts and are not deleted. O1 has no orphan-inventory scanner, repair operation, signed URLs, automatic snapshot completion, public HTTP route or selected production adapter/cloud. PAPER financial facts and the existing immutable terminal-receipt guards remain authoritative.
